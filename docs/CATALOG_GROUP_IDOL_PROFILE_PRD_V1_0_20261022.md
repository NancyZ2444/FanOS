## 1. 背景与现有功能

### 1.1 功能定位

在现有组合、艺人图鉴详情中新增“资料”Tab，集中展示可阅读、可补充、可追溯的档案。用户可以对资料字段、正文及关联关系提出补充、修改、删除建议，平台审核发布后更新正式资料，并形成公开修订记录。

本次按用户要求，以 **QQ 音乐的歌手资料阅读场景**作为主要参考方向，形成 Fan OS 的四板块资料页：简介、基本资料、从艺历程、荣誉记录。简介、历程、荣誉均采用长文本；基本资料按团体与艺人分别定义结构化字段。

| 参考方向 | Fan OS 本次设计口径 |
| --- | --- |
| 进入主体详情后阅读资料 | 组合与艺人详情均提供“资料”Tab，自动识别当前对象 |
| 资料以阅读为主 | 基本资料用“字段名 + 值”展示，其余三板块展示正文，长内容可展开 |
| 经历与荣誉可以按时间组织 | 用户可在正文中写年份标题并分段，也可以不写年份；不要求逐条录入事件或奖项 |
| 用户反馈与可追溯修改 | 在 Fan OS 中补充编辑、后台审核及公开修订历史，记录修订人和生效时间 |

以上为本稿的产品设计方案，不代表 QQ 音乐逐项具备同样能力。[QQ 音乐官方歌手页面](https://y.qq.com/n/ryqq_v2/singer/003fA5G40k6hKc)可作为参考入口；本次公开网页未返回完整资料正文，因此未据此断言其完整字段、排列细节或审核机制。

### 1.2 当前系统与本次差异

| 能力 | 当前实现 | 本次需求 |
| --- | --- | --- |
| 组合详情 | 成员、可选动态、专辑、活动、小卡、其他；头部已有介绍及部分信息 | 新增资料 Tab，集中展示四个板块 |
| 艺人详情 | 可选动态、小卡、专辑、活动、其他；已有简介和个人经历弹层 | 新增资料 Tab，将经历承接为完整资料能力 |
| 基础资料 | 已有名称、多语名称、图片、简介、地区、公司、部分日期与成员关系；后台另有别名、粉丝名、官网等扩展字段 | 统一展示、明确权威数据来源，开放所有公开业务字段的修订建议 |
| 历程 | 艺人现有 period / title / subtitle 简单列表 | 两类对象均使用一个从艺历程长文本字段，支持可选的年份分段；旧内容转换为正文 |
| 荣誉 | 未发现完整的 App 荣誉模型、展示或纠错能力 | 两类对象均新增一个荣誉记录长文本字段及修订审核 |
| 用户纠错 | 自动带入对象、字段原值、修改建议、清空 / 仅说明问题、图片凭证、链接、提交预览 | 扩展为完整资料修订，支持长文本修改、关系增删改及空字段补充 |
| 后台处理 | 图鉴问题纠错、逐字段处理、对象版本检查、正式发布、反馈通知 | 增加资料修订工作区、历程 / 荣誉审核、公开版本发布 |
| 日期资料 | 团体已有出道日期，艺人已有出生日期；艺人当前主体模型没有独立出道日期 | 分别展示团体出道日期、艺人生日与艺人出道日期；补齐艺人出道日期的完整链路 |
| 历史记录 | 本人反馈处理时间线；后台操作日志 | 新增全体有访问权限用户可看的已生效资料版本历史 |
| 待补充 | 当前重提主要支持小卡缺失反馈 | 扩展至资料修订，保留原提交单和每次补充快照 |

当前组合 / 艺人纠错白名单只覆盖部分名称、图片、介绍、日期及艺人本名；名称还会限制为当前可见的最多两个值。直接复用现有表单不足以满足“全部内容支持修改”，本次必须扩展字段及空值编辑能力。

### 1.3 与现有功能的关系

- 本特性归属“已有图鉴数据纠错”，进入后台“图鉴问题纠错”，不进入“小卡缺失收录”。
- 本人反馈进度沿用现有反馈中心及 AI 扫描中的反馈记录入口；资料页可以直达本人的对应提交详情，不新增另一套进度中心。
- 资料页的“修订历史”是公开版本历史，与个人反馈工单、后台操作日志分别管理。
- “我的贡献”继续只展示已收录的小卡，不因本需求扩展为组合 / 艺人资料贡献列表。
- 成员、所属组合、公司经历复用现有关系体系；资料文本不代替实际关系记录。

## 2. 目标、范围与角色

### 2.1 产品目标

1. 用户在组合或艺人详情内即可了解完整资料，不必在多个入口查找。
2. 所有资料内容都有补充或纠错路径，包括当前为空的字段。
3. 用户建议经过审核与正式发布后才影响公共内容，避免未核实信息直接展示。
4. 每次实际生效的修订都能追溯修改内容、修订人和时间。
5. 资料与图鉴主数据保持一致，修订不破坏历史成员、公司及小卡归属关系。

### 2.2 本版范围

| 纳入本版 | 暂不纳入本版 |
| --- | --- |
| 组合 / 艺人资料四板块、完整编辑建议、证据图片、后台审核、部分采纳、补充重提、版本历史、前后对比 | 新增组合 / 艺人主体、音乐播放、自动抓取外部百科、AI 自动生成资料、用户免审发布 |
| 后台直接维护资料也产生发布版本与历史 | 贡献积分、贡献排行榜、把资料贡献加入“我的贡献”Tab |
| 三个正文板块的补充、修改、清空；关联关系纠错 | 历程事件或奖项的结构化管理、自动解析年份 / 奖项、用户自行创建字段定义、任意 HTML、多人实时协同编辑 |

### 2.3 角色

| 角色 | 能力 |
| --- | --- |
| 游客 / 普通浏览者 | 查看公开资料、公开修订历史与前后差异；点击编辑时提示登录 |
| 登录用户 | 对公开资料提交修订；查看本人反馈及审核结果；按要求补充信息 |
| 内容运营 content_operator | 查看审核单、核实证据、编辑拟采用内容、保存处理草稿；沿用现有最终发布权限限制 |
| 管理员 admin | 最终采纳发布、退回补充、拒绝、维护资料、处理异常历史展示 |
| 运营管理员 operation_admin | 沿用现有图鉴权限边界，本版不默认开放图鉴审核与发布权限 |

当前内容运营可以处理编辑，但最终发布 / 拒绝等动作由管理员权限控制。本版不因新增功能放宽既有权限。

## 3. App 资料 Tab 与页面结构

### 3.1 入口与导航

- 组合详情、艺人详情各新增一个“资料”Tab，建议追加在现有 Tab 末尾，保持原有默认 Tab 与浏览习惯。
- Tab 使用稳定标识；动态开关开启或关闭时，不能因下标变化定位错误。
- 保留详情顶部的“反馈问题”；进入资料 Tab 后，增加“编辑资料”和“修订历史”入口。
- 艺人原“个人经历”入口跳转“资料 → 从艺历程”，避免维护两个内容不一致的展示位置。
- 从反馈结果或修订记录进入资料时，定位对应对象和板块，必要时高亮变更字段、正文段落或关联关系。

### 3.2 页面排列

| 顺序 | 区域 | 内容 |
| --- | --- | --- |
| 1 | 资料信息栏 | 最近生效时间、编辑资料、修订历史 |
| 2 | 简介 | 简介正文，长内容展开 / 收起 |
| 3 | 基本资料 | 按团体 / 艺人类型展示对应字段；艺人显示生日、出道日期等 |
| 4 | 从艺历程 | 一个长文本正文，可按年份分段，也可使用连续段落 |
| 5 | 荣誉记录 | 一个长文本正文，可按年份分段，获奖与提名在文字中说明 |

四个板块标题固定，建议提供板块锚点方便跳转。每个板块都有编辑入口，空正文提供“补充内容”。基本资料采用标签和值的列表；简介、从艺历程、荣誉记录采用可阅读的段落正文，保留换行，长内容提供展开 / 收起。不要求用户为了改一个字段填写整页资料。

### 3.3 状态与空内容

- 只展示最新正式发布的资料；审核中的建议不替换当前版本。
- 空板块展示“暂无资料，欢迎补充”，保留补充入口，不能将“无记录”等同于“没有从艺经历 / 未获任何荣誉”。
- 基本资料可在阅读时折叠空字段，但编辑页必须能够展开所有已定义字段并补充空值。
- 加载失败提供重试；对象下架、删除或不可访问时按图鉴权限隐藏资料及历史，不通过历史页绕过限制。
- 同一用户有待处理建议时可显示“你有一条资料修订待处理”，点击进入本人反馈详情；其他用户不看到该提示。

## 4. 板块一：简介

### 4.1 内容与展示

概括组合 / 艺人的定位、出道背景、主要特色与代表经历，使用简洁、中性的事实描述。支持分段文字；本版不新增正文自由图片排版或任意网页内容嵌入。

组合沿用 `description`，艺人沿用 `bio` 的业务内容，不另建一份与头部简介互不更新的长简介。头部可截取同一正式内容展示摘要，资料 Tab 展示全文。

### 4.2 字段与修订规则

| 项目 | 规则 |
| --- | --- |
| 字段 | 组合复用 `description`，艺人复用 `bio`，各为一个长文本字段 |
| 编辑方式 | 多行文本框，支持补充、修改、清空或仅反馈问题；不拆分定位、背景、特色等子字段 |
| 内容格式 | 纯文本，保留换行和空行；不要求填写年份 |
| 字数 | 本稿建议上限 2,000 字；与其他两块长文本分别配置 |
| 审核单位 | 整个简介字段为一个变更项；预览、审核和历史可高亮段落 / 文字差异 |

清空简介须填写原因，但不使图鉴主体名称或身份失效。用户只知道“描述有误”时可选择“仅反馈问题”，填写问题与可核实线索，由运营核实后决定是否改写。

## 5. 板块二：基本资料

### 5.1 团体基本资料（对应现有“组合”）

| 字段 | 类型 / 展示 | 数据规则 |
| --- | --- | --- |
| 官方名称 | 文本，主体必需 | 复用现有主名称，用户可提出更正，不允许正式发布为空 |
| 中文 / 英文 / 韩文名称 | 各自独立文本 | 复用现有字段；全部可编辑，不受头部只显示两个名称的限制 |
| 其他别名 | 文本列表 | 复用后台 aliases，补齐 App 展示及纠错；按名称去重，不自动替代主名称 |
| 组合图片 / 详情封面 | 分别对应图片字段 | 复用现有图片和 cover_image，可上传建议替换图，明确用途 |
| 出道日期 | 日期，选填 | 复用组合 `debut_date`；记录团体正式出道日期，未知可为空，不编造月日 |
| 地区 | 文本或既有地区选项 | 复用 `region`，不将地区自动推断为成员国籍 |
| 活动状态 | 如活动中、暂停活动等业务状态 | 复用 business_status 等既有业务口径；与平台上架 / 审核状态分开 |
| 粉丝名称 | 文本 | 复用 fandom_name，允许补充或更正 |
| 官方网站 / 官方账号 | 外链及平台账号条目 | 复用官网和官方账号关系；可提出更正，但不自动授予认证或修改抓取任务 |
| 经纪公司 | 当前关联 + 历史经历入口 | 来自公司关系，修改通过公司与有效期记录处理 |
| 现成员 / 历史成员 | 关联艺人列表 | 复用成员经历；可提出新增、修正加入 / 退出时间及状态等建议 |
| 成员人数 | 根据成员关系计算 | 支持反馈，通过修订成员记录更正，不手填一个与成员名单矛盾的数字 |

### 5.2 艺人基本资料

| 字段 | 类型 / 展示 | 数据规则 |
| --- | --- | --- |
| 官方艺名 / 名称 | 文本，主体必需 | 复用主名称，正式发布不能为空 |
| 中文 / 英文 / 韩文名称 | 各自独立文本 | 复用全部对应字段，允许补空值 |
| 本名 | 文本 | 复用现有字段，资料未确认时可为空 |
| 其他别名 | 文本列表 | 复用后台 aliases，补齐 App 展示及纠错，与主名称分别维护 |
| 艺人图片 / 详情封面 | 分别对应图片字段 | 复用现有图片和 cover_image，可提交替换图 |
| 生日（出生日期） | 日期，选填 | 复用艺人 `birth_date`；完整日期按 YYYY-MM-DD 展示，未知可为空 |
| 出道日期 | 日期，选填，本次新增独立字段 | 艺人新增 `debut_date`，记录首次正式出道日期；与生日、入团日期、团体出道日期分别维护 |
| 地区 | 文本或既有选项 | 复用 `region` |
| 性别 | 选填 | 复用已有公开资料字段，不根据姓名或图片推断 |
| 活动状态 | 选填业务状态 | 与平台发布状态分开，按既有字典展示 |
| 粉丝名称 | 选填文本 | 复用 fandom_name |
| 官方网站 / 官方账号 | 外链及平台账号条目 | 复用既有数据，账号标识和地址可提建议，内部认证及同步控制不可修改 |
| 所属组合及成员经历 | 关联组合 + 时间范围 / 状态 | 支持多段经历、历史组合及当前身份，不只覆盖一个组合名称 |
| 组合内职务 / 角色 | 关联成员经历的角色 | 与对应组合及有效期一起修订；旧 role 文本作为兼容数据，不覆盖全部经历 |
| 经纪公司 | 当前关联 + 历史经历入口 | 复用公司关系及有效期 |

团体和艺人使用不同的基本资料表单。团体不展示生日、本名、性别等个人字段；艺人保留生日和出道日期两个独立入口，已有空值也能补充。以上除主名称外均允许资料暂缺，不强制用户一次填满。

其他公开资料字段后续由平台字段配置扩展，不让用户自行添加任意字段。国籍、出生地、职业、代表作品、身高、血型等可作为后续讨论项；本版不因参考 QQ 音乐而直接新增全部字段或要求补齐。

### 5.3 “全部支持修改”的范围

1. 四个资料板块中的所有业务内容均提供修改、补充、删除或“仅反馈问题”入口，包括空字段、图片、成员及公司关系。
2. 对派生内容，如成员人数，入口引导用户修订产生该值的源数据；不设置互相矛盾的第二份数字。
3. 删除必要身份字段可以作为问题提交，但运营必须给出有效替代值或说明不采纳，不能发布不满足图鉴校验的内容。
4. 图鉴 ID、审核状态、修订人、修订时间、权限与后台内部备注属于系统记录，不作为用户可编辑的资料字段。
5. 本人的名称备注属于个人偏好，不作为官方名称修订提交；编辑页显示真实官方值，避免把个人备注写进图鉴。

### 5.4 关联数据修订

用户优先搜索已有公司、组合或艺人并提交具体关系建议；缺少关联对象时填写名称和说明作为审核线索，不自动创建主体或仅凭同名完成绑定。

官网及官方账号按平台、显示名称、地址或账号标识提交更正；审核时确认身份对应关系。用户建议不改变后台账号认证、抓取开关、同步频率等内部控制。若修订公司名称本身，使用既有公司纠错流程；本资料单只处理主体与公司的归属关系。

成员 / 公司经历按稳定关系 ID、开始时间、结束时间、状态和必要角色信息编辑。审核时沿用历史有效期及归属校验：当前成员退出不改写其过去发行小卡的归属，公司变更不覆盖旧公司经历。

“删除关系”在用户侧是纠错建议，不直接物理删除历史：正常退出或解约通过结束有效期处理；错误建立的关系可以建议作废，后台保留原记录、作废原因和修订链。关系作废及其公开展示属于本次需要补齐的能力。审核须展示受影响小卡及其他关系，解决历史归属校验后才能发布，不能只删掉资料页上的一行。

一单以一个组合或艺人为主对象；涉及共享关系的修订需列出受影响对象并同步保持双方展示一致。不得把关系整表替换或通过修改简介间接更改成员数据。

### 5.5 生日与出道日期口径

- **艺人生日**：出生日期，使用 `birth_date`；团体不适用该字段。
- **团体出道日期**：当前团体的正式出道日期，复用组合 `debut_date`。
- **艺人出道日期**：本稿默认首次可核实的正式从艺出道日期，新增艺人独立 `debut_date`。后续加入新组合、个人出道、再次出道等经历可写入从艺历程；不能直接覆盖首次出道日。
- 不从生日、入团日期或团体出道日期推算艺人出道日。若出道口径存在争议，提交说明与证据，由后台核实。
- 本版结构化日期沿用完整日期格式；只知道年份时保留字段为空，在修订说明或正文说明已知年份，不填默认的 01-01。
- 当前通用纠错曾用 `release_date` 表达不同对象日期；新资料表单、接口、审核和历史必须使用明确字段键与中文名。旧反馈按对象类型兼容：组合映射其出道日期，艺人映射出生日期，不能把旧艺人日期反馈当作出道日。
- 艺人出道日需同步补齐数据存储、App 模型、详情展示、后台编辑、纠错配置、版本快照及历史对比；不能只在文档或界面增加一行。

## 6. 板块三：从艺历程

### 6.1 长文本字段

| 项目 | 规则 |
| --- | --- |
| 字段 | `career_text`，组合与艺人各自保存一个从艺历程长文本字段（字段键为设计建议） |
| 必填 | 否，允许为空；补充时无需填写其他板块 |
| 编辑方式 | 多行文本框，可直接输入或粘贴完整正文，不拆分事件标题、日期、关联作品等字段 |
| 内容格式 | 纯文本，保留换行和空行；年份可以单独一行，也可写在段落中 |
| 年份要求 | 可选，无强制格式；没有明确年份也能正常提交 |
| 字数 | 本稿建议上限 20,000 字，独立于修订说明及通用短文本限制 |
| 审核单位 | 整个 `career_text` 为一个变更项，无事件条目 ID |

组合可描述成立、出道、重要发行、巡演及成员变动；艺人可描述出道、重要作品与职业阶段。正文仅记录叙述，不自动创建专辑、活动或更改成员关系。

### 6.2 展示与编辑

按保存的正文顺序展示，支持展开 / 收起。可提示用户按年份分段、同一篇采用一致顺序，但系统不解析年份、不自动排序、不生成逐年事件列表，也不按事件分页。

编辑框自动带入当前完整正文，用户可增删其中任意文字；提交时记录该字段的完整建议值及基准值。阅读和编辑均保留换行，公开历史可定位新增、修改或删除的段落。

可选输入示例（仅演示格式，不是事实资料或必填模板）：

```text
2024年
正式出道，发布首部作品。

2025年
开展巡演，并参与新的合作项目。
```

也可直接填写“正式出道后持续开展音乐及演出活动……”等连续文字，不要求补齐年份。

### 6.3 与既有艺人经历兼容

现有 `careers` 中的 `period / title / subtitle` 按原顺序保留，逐项将非空内容用换行拼接，再以空行连接为从艺历程正文。保留原时间描述，不推断年份或补造月日；迁移前保存原始结构快照以便核对及回退，不自动认定某用户为贡献者。拼接后超出新字数上限的旧正文按第 14 章兼容，不截断内容。

新资料页与原经历入口读取同一正式内容。任意长文本不能保证无损拆回旧事件结构；旧客户端需要只读兼容展示或提示升级，不能继续用旧列表覆盖新的正文。成员和公司历史仍使用原结构化关系，不随本次长文本调整而扁平化。

## 7. 板块四：荣誉记录

### 7.1 长文本字段

| 项目 | 规则 |
| --- | --- |
| 字段 | `honors_text`，组合与艺人各自保存一个荣誉记录长文本字段（字段键为设计建议） |
| 必填 | 否，允许为空 |
| 编辑方式 | 多行文本框；不拆分奖项名称、机构、届次、结果、关联作品等输入字段 |
| 内容格式 | 纯文本，保留换行和空行；可按年份分段，也可用连续段落或逐行文字 |
| 年份要求 | 可选，不要求每项内容单独填写年份 |
| 字数 | 本稿建议上限 20,000 字，独立于修订说明及通用短文本限制 |
| 审核单位 | 整个 `honors_text` 为一个变更项，无奖项条目 ID |

### 7.2 展示与内容口径

- 按保存的正文顺序展示，长内容展开 / 收起；不自动解析、排序、统计奖项或识别重复奖项。
- 获奖、提名、入围的区别由文字表述并由后台核实，不强制用户选择结果枚举，也不能将提名审核为获奖。
- 组合获奖不自动记为每位成员个人获奖；个人荣誉不自动写入组合。联合荣誉在正文中明确主体，并提供核实依据。
- 支持补充、修改、清空或仅反馈问题。重复与矛盾内容由审核人员对照正文判断；无实际变化不创建新版本。
- 正文中的作品名为文字，不自动绑定专辑等对象。引用内容与核实材料在修订单中提交，不增加必填的逐奖项来源字段。

可选输入示例（仅演示格式，不代表实际奖项）：

```text
2024年
获得某音乐活动的新人奖。

2025年
凭借某作品获得某奖项提名。
```

### 7.3 三块正文的统一规则

简介、从艺历程、荣誉记录各是一个可独立修订的长文本字段，只有长度限制不同。编辑页提供正文输入、字数提示、修订说明和可选证据；后台按字段对照和采纳，公开历史保存完整正文快照及实际差异。

“只采用一段”通过修改后采纳形成最终全文，不把年份或段落提升为独立审核记录。参考链接、凭证图片放在修订材料区域，仍按既有附件规则管理；不自动嵌入正文。

## 8. 用户提交资料修订

### 8.1 入口和流程

资料 Tab → 编辑资料 / 编辑某板块 / 补充内容 → 自动带入当前对象、正式版本及字段 → 填写建议和原因 → 上传可选凭证 → 预览修改清单 → 提交审核 → 查看本人反馈结果。

不要求用户重新选组合或艺人。入口默认固定当前对象；若使用既有“切换反馈对象”，需确认清空旧建议后重新加载，不允许同一单同时修改两个无关主体。

### 8.2 编辑能力

| 对象 | 可执行操作 | 提交内容 |
| --- | --- | --- |
| 简介 / 从艺历程 / 荣誉记录 | 补充 / 修改 / 清空 / 仅反馈问题 | 字段键、原完整正文、建议完整正文或问题说明、修订原因 |
| 普通基本字段 | 补充 / 修改 / 清空 / 仅反馈问题 | 字段键、原值、建议值、原因 |
| 图片字段 | 替换 / 建议移除 / 仅反馈问题 | 待审核图片资产或问题说明 |
| 成员 / 公司关系 | 新增关系 / 修改关系 / 建议删除 | 关联对象、时间及状态的结构化差异 |

编辑按差异提交，只发送实际修改的字段或关系。每个长文本字段提交完整建议正文及基准值，但不提交整份对象资料覆盖其他字段；成员 / 公司关系仍以稳定关系 ID 定位。空字段和未在头部展示的多语名称也可提交。

### 8.3 输入与证据

- 一单至少包含一项实际变更或一项有效问题说明；与原值相同且无问题说明的内容不能提交。
- 修订说明必填；批量删除 / 作废关系需逐项说明，正文删减或清空按字段说明原因，不要求逐段或逐奖项填写。用户不知道正确值时，可以只说明问题，不能强迫编造答案。
- 建议沿用一单最多 20 个变更项、备注 2,000 字、参考链接最多 6 条、证据图片最多 6 张的现有限制。每个长文本字段各计一个变更项，不按段落、年份或奖项数量计数。简介建议最多 2,000 字，从艺历程及荣誉记录分别最多 20,000 字；需同步更新 App、接口、后台与历史展示，不能继续用通用反馈的 2,000 字校验截断长正文。
- 图片沿用 JPG / PNG / WebP，单张不超过 10 MB；上传完成后才能提交，失败可重试且保留文字。
- 图片字段的“建议替换图”与“证明截图”用途分开。证据图片只供提交人与审核人员查看，不自动成为公开资料图片。
- 本稿建议：补充或修改荣誉事实、修改关键日期或成员 / 公司关系时，至少提供一种核实依据，可为链接、图片或明确出处说明；文字排版等修订不强制提供外链。
- 上传图片进入待审核存储；提交不代表图片已获得展示授权，采用时沿用现有图片发布校验。

### 8.4 提交预览

预览显示对象、涉及板块、操作类型、当前值、建议值、原因和附件数量。三个正文板块按字段展示前后完整内容，可高亮文字 / 段落差异并展开全文；清空展示将移除的原正文。关系的新增与作废单独标记，展示名称、时间和状态，不只显示内部 ID。

提交按钮旁说明：“提交后由平台审核，通过后更新资料并保留你的修订记录。”同时说明公开记录会包含用户昵称及生效时间，证明附件不公开。

### 8.5 草稿、提交与重提

- 编辑中退出提示保留本地草稿；按账号和对象隔离。恢复时重新检查正式版本，避免用旧草稿覆盖最新内容。
- 提交带原版本标识和幂等请求 ID；重复点击或超时重试只生成同一提交单。
- 已提交内容形成不可变快照，用户不能直接覆盖审核员正在查看的版本。
- 同一用户对同一对象已有相同变更待处理时，提示进入原记录并阻止重复提交。无关字段或不同关系可以另建单，不锁住整个对象；同一正文不同段落仍属于同一字段，重叠建议提示已有待处理内容，发布时仍执行字段级冲突检查。不同用户可以独立提出建议。
- “待补充”允许在原单修改并重提，增加提交批次，保留旧快照和处理记录；重提后需重新审核，不沿用上次未完成的采纳决定。
- 本版不增加任意撤回或公开编辑草稿功能；已结束的单据需要进一步修改时创建新单并关联旧结果。

## 9. 后台资料管理与审核

### 9.1 两类后台入口

| 入口 | 作用 |
| --- | --- |
| 图鉴内容管理 → 组合管理 / 艺人管理 → 资料 | 查看当前正式资料，维护四板块，查看发布历史；新增资料草稿与当前公开版分离 |
| 图鉴内容管理 → 图鉴问题纠错 → 资料修订 | 接收用户修订，核实、逐项处理、提交管理员发布或退回补充 |

建议在已有 CORRECTION 下增加“资料修订”业务子类及专用列表视图，不新增一个与通用纠错重复的反馈系统。组合 / 艺人现有资料字段纠错也路由到同一资料发布能力，不能一条路径有历史、另一条路径直接覆盖。

### 9.2 审核列表

筛选项：组合 / 艺人、对象名称或 ID、板块、处理状态、采用结果、提交时间、提交人、处理人。

列表字段：提交单编号、对象与类型、板块、变更摘要、提交人、提交时间、补充次数、处理状态、是否冲突、操作入口。按提交时间排序，使用服务端分页；所有名称均可回看对应对象。

### 9.3 审核详情

| 区域 | 内容 |
| --- | --- |
| 对象与提交信息 | 对象 ID / 名称 / 图片、提交人、提交批次、提交时间、基准版本 |
| 四板块导航 | 定位本次涉及的介绍、基本资料、历程或荣誉 |
| 差异对照 | 提交时原值、用户建议值、当前正式值、拟采用值；长文本保留完整四份正文并支持段落 / 文字高亮 |
| 证据 | 链接、出处说明、图片预览；与拟公开图片分开 |
| 决策 | 每项采纳、修改后采纳、不采纳；必要时整单退回补充 |
| 发布预览 | 本次采纳后完整资料效果、关系影响及将生成的修订摘要 |
| 处理记录 | 内部备注、公开说明、经办 / 审核 / 发布时间及历史批次 |

### 9.4 处理操作

| 操作 | 对正式资料的影响 | 对用户的影响 |
| --- | --- | --- |
| 开始核实 / 保存处理草稿 | 无 | 不因内部保存产生公开动态或结果通知 |
| 采纳原建议 | 暂存拟采用内容，仍需正式发布 | 发布前不显示已收录 |
| 修改后采纳 | 审核员填写实际采用值及说明 | 发布后展示最终采用值，不能把未采用原文当成正式结果 |
| 不采纳 | 不改对应字段，原因必填 | 结束时展示原因 |
| 退回补充 | 不改正式资料，指出缺少材料 | 用户可在原单补充并重提 |
| 确认发布 | 原子更新实际采用项、生成版本与历史、更新反馈结果 | 生成结果通知，并提供资料 / 对应修订记录入口 |
| 已被他人修正 | 无重复变更，不创建空版本 | 说明已修正，可关联已生效版本，但不伪造本单贡献 |

支持部分采纳。三个正文板块分别按字段决定采用结果；若只采纳同一正文中的部分修改，审核员选择“修改后采纳”，基于当前正式正文编辑完整最终值，并说明未采用部分，不能把整篇用户建议都标记为原文采纳。年份、段落、事件及奖项不设独立审核状态。互相依赖的关系字段作为完整变更单元审核，例如成员、加入时间、退出时间、身份状态；不能采纳一半后形成无效关系。任一拟采用项校验失败，整次发布回滚，其他项也不能先写入。

### 9.5 后台主动修订

管理员或内容运营在主体资料页维护内容，同样先形成编辑草稿，按既有权限发布。发布时必须填写修订说明，并记录公开版本；不能通过后台直改、旧纠错接口或导入绕过修订历史。

后台主动发布记录的对外修订人显示“Fan OS 编辑”，内部保留具体操作人和审核人。现有对已发布主体的下架、修改、审核等技术流程可复用，但对外应原子切换，不因暂存资料草稿让整个主体突然消失。

## 10. 状态、本人进度与通知

### 10.1 统一语义

沿用现有反馈状态与结果的分离，不以“审核员已保存意见”代替“资料已生效”。此前需求中“已处理 / 已收录”继续作为本特性结果语义；当前代码的部分标签为“已采用 / 无法采用”，对接时需要明确映射，不能误认为文案已一致。

| 业务阶段 | 后台状态 / 结果 | 本特性 App 建议文案 | 是否产生公开版本 |
| --- | --- | --- | --- |
| 已提交、尚未结束 | PENDING 或 PROCESSING + PENDING | 待处理；内部核实不必逐次对外通知 | 否 |
| 退回补充 | NEEDS_INFO | 待补充信息 | 否 |
| 全部实际采纳并发布 | PROCESSED + INCLUDED | 已收录 · 全部采用 | 是 |
| 部分实际采纳并发布 | PROCESSED + INCLUDED + 明细 | 已收录 · 部分采用 | 是，仅记录实际变更 |
| 全部不采纳 | PROCESSED + NOT_INCLUDED | 已处理 · 未采用，附原因 | 否 |
| 建议已被其他版本修正 | PROCESSED + NOT_INCLUDED + 具体原因 | 已处理 · 已由其他修订更新 | 否 |

当前服务公开文案为“待处理 / 已采用 / 无法采用 / 信息缺失待补充”；上述文案统一属于本次对接要求，不在文档中冒充现状。其他已有场景若暂未统一，需避免同一提交单在不同入口出现不同结果含义。

### 10.2 反馈中心

既有反馈中心继续承载进度，在“数据纠错”内识别资料修订，可增加“资料修订”筛选。AI 扫描入口仍可查看统一反馈记录，资料页的本人待处理提示及结果通知直接打开同一提交详情。

本人详情展示提交内容、补充批次、最终采用值、未采用项和原因、公开处理时间线，以及已生成的资料版本。后台内部备注、未发布的处理草稿和失败发布记录不回传为用户结果。

### 10.3 通知

退回补充、最终采用、最终未采用时生成站内结果通知。部分采用必须写明，不使用“全部已修改”的笼统提示。

内部开始处理、草稿保存、发布失败和无变化重试不发结果通知。通知与成功提交的发布结果关联，失败可以重试发送，但不能回滚已经成功的公开版本或重复通知用户。

## 11. App 公开修订历史

### 11.1 可见范围

“修订历史”仅展示已正式生效的版本，包括用户建议被采用、后台主动修订、管理员纠正旧版本。待审核、待补充、未采用的提交不进入公开历史，只在本人反馈和后台可见。

历史入口位于资料页信息栏；可按板块筛选，默认按发布时间倒序。历史版本只读，不提供用户直接恢复旧版或修改修订人、时间的操作。

### 11.2 历史列表字段

| 字段 | 展示规则 |
| --- | --- |
| 版本号 | 按对象独立递增，如 V1、V2、V3；仅实际生效版本递增 |
| 修订人 | 被采用建议的用户昵称及主页链接；后台主动修订显示“Fan OS 编辑” |
| 修订时间 | 本版本正式生效时间，精确到分钟；存储原始时间，按 App 统一时区规则展示 |
| 修改摘要 | 如“更正出道日期，补充 2025 年荣誉内容”；由实际采用差异生成，不依赖自动统计奖项 |
| 涉及板块 | 介绍 / 基本资料 / 从艺历程 / 荣誉记录 |
| 发布来源 | 用户修订、平台修订、历史资料初始化、系统依据已审核关系更新 |
| 操作 | 查看差异、查看该版资料 |

资料页“最近更新”取最近正式版本时间，不使用用户提交时间、审核草稿保存时间或无关主数据更新时间。

### 11.3 版本详情

展示本版本全文或板块快照，以及与前一正式版的差异：基本资料字段旧值 → 新值、长文本正文的增删改高亮、关系新增 / 修改 / 作废，以及必要的公开修订说明。长文本差异以文字 / 段落展示，不生成逐年份或逐奖项的版本记录。被删除的文字或作废关系仍可在相应历史版本中查看，除非该内容因权限或合规原因被限制展示。

旧版名称、成员、公司、历程 / 荣誉正文和关系展示使用当时的快照，不能每次读取最新主数据导致“旧版本也随之改变”。关联对象可用时可跳转到当前详情，明确链接指向当前页面。

修订详情可同时展示“提交时间”和“生效时间”，但“修订时间”统一指生效时间，避免混淆。本版一份提交单最多执行一次最终发布，在主对象中生成一个正式版本；共享关系影响其他对象时，按 12.2 同时生成各受影响对象的版本。部分采用后该单结束，其余建议明确不采用或已由其他版本修正，需要继续补充时另提新单。不提供“先发布一半、剩余仍待补充”的混合状态。

### 11.4 修订归属与账号变化

- 用户原建议直接采用：记录该用户为修订来源；审核员另存为后台审核人。
- 修改后采纳：保留用户的建议来源，并标记“平台核实调整后采用”；实际采用差异与最终编辑责任分别保存。
- 用户只提供线索、未贡献实际采用内容时，可标记为线索来源；不得把平台独立新增的整段内容都归为用户原文。
- 本版不提供多单合并发布，主提交单来源归属提交人；因共享关系同步的其他对象版本关联同一真实来源。归属模型可预留多贡献者，但不能把最后点击发布的人当作用户建议的贡献者。
- 关系到期等系统自动更新显示“系统更新”，关联原批准关系及其来源；不伪记为原用户在更新当天再次主动提交。
- 保存用户稳定 ID 与提交时昵称快照。公开历史默认展示当时昵称，主页仍指向同一稳定用户；账号注销时显示“已注销用户”并移除链接。
- 头像 / 昵称违规、主页不可访问或相关内容需隐藏时采用占位，不公开手机号、登录账号、后台人员真实姓名或内部 ID。

### 11.5 历史纠正与限制展示

更正过去的错误内容应形成新版本，保留原版本和纠正关系，不能修改旧快照来伪装“从未出现错误”。如需参考旧版恢复内容，管理员将其作为新的候选修订，重新校验并发布新版本，不直接回拨版本号。

已撤销展示授权的图片或不宜公开的历史文本可限制公开展示，显示“该部分内容暂不可查看”；原始审计保留在有权限的后台。历史保存不代表所有旧内容都必须继续对外展示。

## 12. 并发、关联一致性与发布规则

### 12.1 并发修订

提交保存基准资料版本；审核详情同时显示提交原值和当前正式值。发布时间再次校验，不能只在打开审核页时检查一次。

| 情况 | 处理 |
| --- | --- |
| 正式内容未变化 | 按审核结论发布 |
| 其他用户只修改了无关字段 / 关系 | 基于当前正式版应用本次已审核差异，不覆盖无关改动；记录实际父版本 |
| 同一字段或关系已经变化 | 标记冲突，要求审核员重新对比并确认采用值；同一长文本的不同段落或不同年份也按同字段冲突，不静默覆盖或自动拼接 |
| 建议值已等于当前正式值 | 标记已修正，不重复写入，不生成空版本或虚假贡献 |
| 待作废关系已被修改 / 作废 | 重新核实；不能按旧数组下标删除另一条关系 |
| 发布按钮重复点击 | 同一请求只产生一份公开版本、一组结果记录和通知事件 |

例如用户 A 更正出道日期、用户 B 修改荣誉正文，A 先发布后，B 可以基于新版本修改荣誉而保留 A 的日期。如果两人都修改从艺历程，即使分别修改 2024 年和 2025 年段落，也按同一字段冲突处理；审核员对照原文、当前全文和建议全文，人工合并并重新确认最终值后发布。

### 12.2 关联关系一致性

- 日期、成员状态、公司有效期等遵循现有校验，不以资料页编辑绕过历史归属规则。
- 同一关系修改影响组合和艺人两侧时，在同一发布事务中更新关系，并为公开资料实际改变的每个对象各生成一个版本，用同一发布事件关联；不能只记关系日志而不更新另一侧资料版本。
- 关系随时间生效、失效造成的展示变化，同样为受影响对象生成系统更新版本，关联原批准关系、有效时间和处理时间；按关系及生效节点防重复，不得在公开历史之外无痕改变成员或公司展示。
- 基本资料和头部摘要从同一正式数据读取；资料版本发布后刷新相关详情与搜索展示。用户个人名称备注仍保留为个人偏好。

### 12.3 发布原子性

正式资料更新、关联关系变更、公开版本快照、逐项归属、反馈采用结果和待发送通知事件须原子提交。任一项校验失败，整次不生效，不能出现“已收录但资料未变”或“资料已变但没有历史”。

同一操作允许拒绝部分建议后发布其余有效内容；但已经决定采纳的项必须整体通过校验。未采纳项保留原因，不能在发布时静默遗漏。

## 13. 数据与接口要求

### 13.1 逻辑数据对象

以下是业务模型建议，不要求机械新建同名表；应复用现有图鉴和反馈存储，补齐版本化能力。

| 对象 | 关键内容 |
| --- | --- |
| 当前资料 | entity_type、entity_id、当前公开版本、基本资料、三个长文本正文及关联引用 |
| 三个正文 | 组合 `description` / 艺人 `bio`、`career_text`、`honors_text`；保存完整文本和换行，无事件 / 奖项子表要求 |
| 基础日期 | 团体 `debut_date`；艺人 `birth_date` 及新增 `debut_date`，分别记录，允许未知为空 |
| 修订提交单 | 复用 CORRECTION，新增资料修订标识；提交人、对象、基准版本、变更清单、原因、证据、请求 ID |
| 提交批次 | 每次提交 / 补充的不可变快照和时间，关联同一单据 |
| 审核决定 | 逐字段 / 逐关系原建议、最终采用值、结论、原因、经办人、审核人；正文以完整最终值为准 |
| 公开资料版本 | 对象、递增版本号、实际父版本、发布快照、差异、来源单据、公开修订说明、生效时间 |
| 归属记录 | 版本及变更项对应的用户、昵称快照、平台调整标记、内部审核关系 |
| 关系与历史映射 | 稳定关系 ID、关联对象 ID、有效期、影响对象；旧经历结构快照及其正文迁移来源 |

版本的判定范围须覆盖这四个板块及相关成员 / 公司关系，不能只计算主体一行记录的更新时间。原有后台 OperationLog 用于审计，可以继续保留，但不能直接作为 App 的公开版本接口。

### 13.2 字段配置与操作契约

字段定义需包含：字段键、中文名、对象适用范围、板块、类型、是否可清空、长度 / 日期约束、关联对象类型、当前值及编辑提示。

编辑数据接口返回完整可修订字段定义，包括当前为空或头部未展示的名称；公开阅读接口与编辑接口按需要分别返回，禁止直接暴露后台 metadata。

正文和普通字段沿用设置、清空、仅说明问题语义。三个正文以字段键、基准全文、建议全文提交，不接受事件条目 ID 或逐年操作。关系变更以 `ADD / UPDATE / DELETE` 加稳定关系 ID 表达；新增关系由服务端分配正式 ID，删除执行审核后的作废规则。

字段配置分别标明简介上限 2,000 字、从艺历程和荣誉记录各 20,000 字、修订说明上限 2,000 字；文本按用户可见字符计数、换行计入，前后端统一。关联关系单独定义结构校验，不能套用通用短文本验证后直接落库。新增正文超限应提示修改，不静默截断；历史超限正文按第 14 章提供对应字段的兼容上限。App、审核页、快照、差异及旧接口适配共同覆盖完整正文。

### 13.3 接口能力清单

| 能力 | 要求 |
| --- | --- |
| 获取资料 | 组合 / 艺人当前正式版本及四板块数据，携带版本标识 |
| 获取可修订定义 | 登录后按团体 / 艺人返回各自完整字段、三个正文的长度配置、关联选项与基准版本 |
| 提交资料建议 | 复用反馈提交链路，支持长文本字段建议值、普通字段与关系差异、图片证据、版本与幂等校验 |
| 待补充重提 | 扩展现有重提能力至资料修订，校验本人权限与原单状态 |
| 本人反馈 | 统一反馈中心列表、详情、最终逐项结果及公开版本跳转 |
| 后台列表 / 详情 | 增加资料修订筛选、正文与字段对比、关系影响、字段级版本冲突 |
| 后台处理 / 发布 | 按权限保存草稿、退回、拒绝、原子发布 |
| 公开历史列表 / 详情 | 按对象分页，支持板块筛选、版本快照、差异与公开归属；不带内部证据 |
| 后台主动发布 | 同一版本化发布服务，覆盖旧编辑 / 导入 / 纠错路径 |

路由命名在技术设计阶段确定；现有 `/feedback`、`/admin/console/feedback` 可扩展，不能把本清单当成已经存在的新接口。

## 14. 初始化与兼容

1. 保留既有组合 / 艺人 ID、收藏、本命、名称备注、图片、小卡和来源关联。
2. 将现有已发布简介、基础资料、成员 / 公司关系与艺人经历映射为资料初始版本。旧 `careers` 按 6.3 保真转换为正文，保留原结构快照；缺失简介、组合历程、荣誉及艺人出道日保持为空，不自动生成事实或推算日期。
3. 初始版本标识“历史资料初始化”，修订人显示“系统整理”；初始化时间与已有数据时间分别记录。没有可信历史作者或时间时不推断、不冒认。
4. 旧后台操作日志不批量公开，也不伪装成完整的用户修订链；只有能可靠重建的发布记录才可另行核验导入。
5. 既有待处理组合 / 艺人纠错保留原单、原证据和原值；在新审核页兼容展示，实际发布时生成新资料版本。
6. 简介复用现有字段；旧经历读取按兼容方案展示同一正式正文。可将全文作为一个只读兼容内容返回，须验证旧客户端展示与长度；不支持的版本提示升级，不能返回过期旧列表冒充最新内容，也不承诺将任意正文无损拆回旧结构。旧经历写入入口需接入正文修订或停用，不维护两份可独立修改的正式数据。
7. 迁移先备份并在副本核对，验证字段、关系、原经历内容与顺序、换行、长正文完整性、状态和历史引用；本文仅提出要求，没有执行迁移或发布。
8. 历史正文已超出新字数上限时，初始化与历史快照仍保留全文，阅读、审核和差异展示不能截断，也不因超限拒绝初始化。该字段后续修订允许维持或缩短当前正式正文长度，不允许继续增加；编辑接口返回相应兼容上限，发布时再按当前正式值校验。整理到标准上限内后恢复标准限制，不能因旧版本曾较长再次放宽。

## 15. 边界与异常处理

| 场景 | 产品处理 |
| --- | --- |
| 游客编辑 | 引导登录，登录后返回原对象及板块 |
| 资料为空 | 四板块保留入口，允许补充，不强制整页填满 |
| 编辑未改内容 | 禁止无意义提交；仅说明问题需有有效说明 |
| 主名称被建议清空 | 可接收问题，发布前须有效替代或拒绝，不能产生无名图鉴 |
| 只知道年份或没有年份 | 历程 / 荣誉按原文字保存，年份可选、不做日期解析；基本资料日期不编造月日，可附说明待核实 |
| 关联对象不存在 | 留审核线索，不按名称自动新建或绑定 |
| 图片上传失败 | 保留文字和已成功上传附件，重试后继续 |
| 提交 / 发布超时 | 相同请求 ID 重试确认，避免重复单据或版本 |
| 待审核期间对象有新版本 | 按字段 / 关系判断冲突；同一正文不同段落仍需人工核对，不能全量覆盖对象 |
| 荣誉正文重复描述 | 由审核员对照文本核实和整理，不承诺自动识别奖项；未变化不新增版本 |
| 作品 / 关联对象下架 | 按权限隐藏链接或内容，保留可公开的历史事实 |
| 主体下架或删除 | 停止公开资料与历史访问；未结束单据转为对象不可用待处理，不自动发布 |
| 只采纳部分内容 | 展示实际采用项及未采用原因，历史仅记录实际差异 |
| 后台保存草稿失败 | 不改变正式资料、反馈结果或公开历史 |
| 用户改名 / 注销 | 保留稳定归属，昵称快照或注销占位，不丢历史记录 |
| 历史内容需限制展示 | 对外脱敏或占位，后台审计保留，不能用历史链接绕过 |
| 账号切换 / 离线草稿 | 按账号和对象隔离；上线后校验版本再提交 |

## 16. 非功能与质量要求

- 资料 Tab 按需加载；三个正文板块支持展开 / 收起和按需渲染，不以年份或事件分页。修订历史列表分页，初始建议每页 20 条，不在列表加载所有版本全文和附件。
- 编辑过程中保留未提交文本，上传或校验失败不得清空用户输入。
- 文本采用安全的受限格式展示，不执行用户 HTML 或脚本；外链不自动抓取执行。
- 用户只能读取自己的反馈和证据；公开历史使用独立字段白名单，不直接返回后台审核对象。
- 提交人、修订人、审核人及时间由服务端确定，不信任客户端伪造；图片需校验归属与用途。
- 版本号单调递增，快照不可原地改写。需要限制公开内容时记录限制行为，不抹除内部追溯。
- 图片权限、关系历史、用户昵称和公开版本的缓存策略一致；发布成功后各详情入口可读取同一版本。
- 本版不承诺固定审核时效；若后续设置 SLA，再增加运营排班和超时提醒规则。

| PF-06 | 个人名称备注存在 | 编辑带入官方值，不把个人备注提交为官方名 |
| PF-07 | 修改成员人数 / 公司 | 引导修改源关系及有效期，双方展示一致，历史小卡归属不被重写 |
| PF-08 | 补充 / 修改 / 清空历程 | 单个长文本输入，无事件子字段；保留正文换行，只修改该字段，不覆盖其他资料 |
| PF-09 | 编辑荣誉正文 | 不要求逐奖项填写机构 / 结果 / 年份；正文清楚区分获奖与提名，组合奖不自动扩散到成员 |
| PF-10 | 荣誉正文含重复描述 | 人工对照核实，不依赖自动奖项去重；无实际差异不创建空版本 |
| PF-11 | 图片与凭证 | 替换图和证明图区分，凭证不会公开显示为资料图片 |
| PF-12 | 提交前预览 | 正确显示原值、建议值、新增 / 删除项及原因 |
| PF-13 | 用户提交后刷新资料 | 仍为当前正式版本，待审建议不提前公开 |
| PF-14 | 重复提交或超时重试 | 一次请求只生成一个单据；相同待处理变更不重复提交，无关字段仍可新建单 |
| PF-15 | 后台审核入口 | 资料修订进入图鉴问题纠错，与小卡缺失收录分开 |
| PF-16 | 审核四值对比 | 可同时查看原值、用户建议、当前正式值和拟采用值 |
| PF-17 | 内容运营保存审核草稿 | 可保存意见，不能越权最终发布 / 拒绝，不生成结果通知 |
| PF-18 | 全部 / 部分采纳发布 | 正式资料、版本历史、归属和反馈结果一起更新 |
| PF-19 | 任一采用项校验失败 | 全部拟发布变更回滚，不显示已收录、不发成功通知 |
| PF-20 | 不采纳 / 待补充 | 原因必填；不产生公开版本；本人收到对应结果 |
| PF-21 | 资料修订补充重提 | 原单不变、批次递增、旧快照保留，重新审核新提交 |
| PF-22 | A 改日期，B 改无关荣誉 | B 发布不覆盖 A；记录实际父版本 |
| PF-23 | 同一正文的不同年份 / 段落先被修改 | 仍判为同字段冲突，人工合并并重新确认最终全文，不能静默覆盖或自动拼接 |
| PF-24 | 建议已被其他用户修正 | 标记已修正，不创建重复版本或虚假贡献 |
| PF-25 | 查看公开修订列表 | 有版本、修订人、时间、摘要、板块及详情入口 |
| PF-26 | 查看旧版本 | 显示当时快照，不随最新名称、关系或公司变化而改写 |
| PF-27 | 查看版本差异 | 正文展示实际采用的文字 / 段落增删改并可看全文；普通字段和关系分别对比，未采用建议不混入 |
| PF-28 | 修改后采纳 / 后台主动编辑 | 贡献来源与平台编辑、审核责任区分，不错误署名 |
| PF-29 | 待审核、被拒单据 | 只在本人反馈和后台可见，不进入公开历史 |
| PF-30 | 账号改名 / 注销 | 历史归属可追溯，展示昵称快照或注销占位，主页权限正确 |
| PF-31 | 反馈进度与我的贡献 | 复用统一反馈中心；组合 / 艺人资料不加入小卡贡献 Tab |
| PF-32 | 图鉴主体不可访问 | 资料和历史均受限制，旧历史链接不可绕过 |
| PF-33 | 后台直接修改或旧纠错接口发布 | 进入同一版本化服务，不能绕过公开历史 |
| PF-34 | 初始化旧资料 | 保留原数据和关系；旧经历按原顺序保真拼接，保留原结构备份；不凭空生成日期、作者或荣誉，不让旧列表覆盖新正文 |
| PF-35 | 重复点击发布、通知失败重试 | 同一发布事件对每个受影响对象仅生成一份版本；通知可恢复发送且不重复 |
| PF-36 | 未授权读取他人反馈 / 证据 | 拒绝访问，公开历史不泄漏内部字段 |
| PF-37 | 关系到期影响资料展示 | 记录依据已审核关系的系统更新，不发生无痕变更 |
| PF-38 | 参考旧版纠正资料 | 生成新的正式版本，原版本保留，版本号不回拨 |
| PF-39 | 正常退出与错误关系删除建议 | 正常变更结束有效期；错误关系作废留痕，历史关联受保护，不直接物理删除 |
| PF-40 | 共享成员关系变更 | 组合和艺人实际变化的资料分别生成版本，同一事件原子生效，不出现单侧新旧不一致 |
| PF-41 | 查看 / 修改艺人生日及出道日 | 两个独立日期字段、独立审核和历史；不会映射到同一通用日期，不从团体出道日或入团日推算 |
| PF-42 | 切换团体 / 艺人对象 | 返回各自基本资料表单；团体无生日，艺人有生日和出道日；空值可补充但不强制整表填满 |
| PF-43 | 正文有年份 / 无年份 | 均可提交并保留原段落与顺序，不自动排序、不要求逐年必填、不按年份分页 |
| PF-44 | 超过 2,000 字但未超过 20,000 字的历程 / 荣誉 | App、提交、后台、发布快照、公开资料和历史均完整保留；超过字段上限明确提示，不静默截断 |
| PF-45 | 只采用正文中的部分修改 | 修改后采纳保存完整最终正文，显示实际差异及平台调整标记；年份与段落不产生独立审核状态 |
| PF-46 | 迁移后旧正文超过新上限 | 完整保留、可读可审；后续修订不增加当前正式长度，降到标准上限内后恢复标准校验，不截断或双轨维护 |

## 19. 讨论默认值与更新记录

### 19.1 本稿建议的产品口径

以下已给出可执行默认方案，后续可以直接修改对应章节：

| 讨论项 | 本稿默认 |
| --- | --- |
| 资料 Tab 位置 | 追加到详情 Tab 末尾，保持原默认页 |
| 资料页参考 | 以 QQ 音乐资料阅读场景为主参考；四板块及审核历史按 Fan OS 本稿定义 |
| 正文结构 / 顺序 | 简介、历程、荣誉各一个长文本；年份分段可选，按保存顺序展示，不自动重排 |
| 正文长度 | 简介 2,000 字；历程和荣誉各 20,000 字；修订说明单独 2,000 字 |
| 基本资料 | 团体和艺人分别配置；艺人生日与首次正式出道日期独立，未知允许为空 |
| 公开历史范围 | 仅已生效版本；未采用和待审只本人及后台可见 |
| 修订时间 | 正式生效时间，提交时间在详情单列 |
| 公开署名 | 用户昵称快照可跳主页；平台主动修改显示 Fan OS 编辑 |
| 证据要求 | 一般修改不强制外链；荣誉、关键日期和关系修订至少一种可核实依据 |
| 单次提交容量 | 最多 20 项变更、6 张证据图、6 个链接，沿用现有单据规模 |
| 关系更改 | 修订真实关系及有效期，不能覆盖历史或另存展示字符串 |
| 状态文案 | 资料采用结果按“已收录 / 已处理”语义与当前“已采用 / 无法采用”做统一映射 |
