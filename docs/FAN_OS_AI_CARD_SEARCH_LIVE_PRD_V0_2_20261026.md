## 1. 核心建议：两个功能在 App 里分别怎么做

**描述找卡做成“带追问能力的找卡页”；动态小卡做成“网格管理 + 竖向全屏播放”的个人动态作品库。**

| 用户关心的问题 | 推荐结论 |
| --- | --- |
| 动态小卡是否像“已拥有”一样展示？ | 可以放在同级入口，采用熟悉的网格浏览，但它记录“我生成的作品”，不是“我拥有实体卡”的状态 |
| 是否有相册模式？ | 首期提供相册式网格图库；暂不新建翻页式动态相册作品。需要分类整理时后续增加轻量合集 |
| 是否像抖音一样？ | 借鉴上下滑切换、当前作品播放的交互；首期浏览自己的作品或某个公开主页，不建设算法推荐广场 |
| 描述找卡是否做纯聊天？ | 推荐以真实小卡结果为主，条件和追问辅助；不用一屏聊天气泡承载找卡 |
| 两个功能怎么衔接？ | 找到目标 → 查看原图鉴详情 → 用户明确点击生成动态 → 成品进入个人动态库 |
| 是否新增底部一级导航？ | 首期不新增；融入“图鉴、扫描、收藏、我的”现有入口 |
| 最终是不是一张 Live 图？ | 推荐默认在已验证的 iOS 设备交付 1 件可播放作品及 1 张可保存的 Live Photo；其他设备明确展示实际支持格式 |

本文中“相册式网格”是浏览形式；已有“相册模式 BOOK / 卡片模式 CARDS”是数字卡册作品类型。二者分别定义。网格进入全屏播放不属于卡册模式切换。

## 2. 现有结构与新增对象的关系

### 2.1 本轮核对的 App 现状

| 位置 | 当前本地实现 | 本次调整 |
| --- | --- | --- |
| 底部导航 | 首页、图鉴、扫描、收藏、我的 | 保留五个入口 |
| 图鉴搜索 | 普通关键词搜索，含组合、艺人、专辑、小卡、用户等类别 | 增加独立“描述找卡”入口，结果只针对小卡 |
| 收藏 | 已拥有、心愿单、卡册；已拥有支持网格 / 列表、图文 / 纯图 | 新增“动态卡”同级 Tab |
| 我的主页 | 已拥有、心愿单、卡册、我的贡献 | 增加“动态卡”Tab，本人与访客可见范围不同 |
| 小卡详情 | 原始正反面、拥有数量、心愿关系等 | 增加“让小卡动起来”与“我的动态作品” |
| 卡册作品 | BOOK / CARDS 创建后固定，允许使用未标记拥有的可用图鉴卡 | 本次不改作品类型，也不直接接入动态视频元素 |

上述为本地代码核对，未核验生产部署。现有扫描仍是图片特征匹配；描述检索、动态作品库和视频播放 / 导出都需要新增。

### 2.2 必须独立的几个概念

| 概念 | 含义 | 是否由生成动作改变 |
| --- | --- | --- |
| 已拥有 | 用户声明拥有多少张某款实体小卡 | 否 |
| 心愿单 | 用户想要该款小卡 | 否 |
| 卡册 | 引用图鉴小卡进行设计和展示的作品 | 否，不自动添加 |
| 我的动态作品 | 用户基于某张图鉴卡生成的衍生作品 | 成功生成新增一件 |
| 公开状态 | 动态作品是否允许他人查看 | 默认私有，需用户主动发布 |
| Live Photo 导出能力 | 该作品能否按目标设备格式保存 | 由文件规格、封装和设备能力决定 |

例如：同一张图鉴卡，用户已拥有 2 张，生成了 3 个动态作品。界面分别显示“已拥有 ×2”和“我的动态作品 3”，不能合并成 5 张。

取消“已拥有”不删除动态作品；删除动态作品不减少实体卡数量；生成失败不产生“已生成”标记。一个 Card ID 可以关联用户的多个动态作品 ID。

**生成不强制先标记“已拥有”。** 选卡时优先提供已拥有列表，也可选择其他符合生成条件的图鉴卡。能否生成由图片可用性、AI 衍生处理条件、模型支持和用户额度共同决定；自报拥有不是授权证明。

## 3. App 信息架构与入口

建议保持以下结构：

```text
图鉴
  ├─ 普通搜索：名称、编号、艺人、来源等
  └─ 描述找卡：描述特征 → 候选卡 → 继续补充 → 小卡详情

扫描
  └─ 辅助入口：没有图片？试试描述找卡

收藏
  ├─ 已拥有
  ├─ 心愿单
  ├─ 卡册
  └─ 动态卡
       ├─ 我的作品：网格 → 点击进入上下滑全屏播放
       ├─ 生成记录：排队 / 生成中 / 处理中 / 完成 / 失败
       └─ 生成动态：选卡 → 效果 → 确认 → 生成

我的主页
  └─ 动态卡
       ├─ 本人：管理自己的全部允许查看作品
       └─ 访客：仅公开审核通过且当前可访问的作品
```

“收藏 → 动态卡”和“我的主页 → 动态卡”读取同一批作品，不复制数据。主操作入口放在收藏，主页承接自我展示。首次上线仍默认打开原有收藏 Tab，不强制把用户带到 AI 功能。

“我的贡献”继续只展示已收录小卡，不加入动态生成记录。图鉴反馈进度仍走原有统一反馈入口，动态生成进度归“生成记录”。

## 4. 功能 2：描述找卡的入口与页面

### 4.1 入口设计

| 入口 | 展示方式 | 自动带入 |
| --- | --- | --- |
| 图鉴首页搜索区域 | 搜索框旁或下方的“描述找卡”按钮 | 全图鉴范围 |
| 普通搜索无结果 / 小卡结果区域 | “记不清名字？描述一下找小卡” | 可带入原输入，用户确认后才执行 AI 检索 |
| 扫描页 | “没有图片？试试描述找卡” | 不自动提交扫描照片，不创建缺卡反馈 |
| 组合 / 艺人详情的小卡列表 | “描述找这一组 / 这位艺人的小卡” | 当前组合 / 艺人作为可移除范围 |
| 收藏中的已拥有列表 | 后续可增加“在已拥有中描述找卡” | 需明确范围；首期主入口默认搜全图鉴 |

普通搜索和描述找卡使用独立页面。普通搜索继续支持多类对象；描述找卡只找小卡，不再向用户展示“用户、组合、专辑”等结果类型切换。

### 4.2 初始页

页面建议包含：

1. 标题“描述找卡”，副标题“说说服装、动作、背景，帮你在图鉴里找”。
2. 多行输入框，默认提示“例如：黑发、白色衣服、蓝色背景，手在脸旁比耶”。
3. 可选范围：全部图鉴 / 指定组合或艺人；从详情进入时自动选中对应范围。
4. 3～4 个可点击示例；点击只填入文本，不立即消耗额度。
5. “开始找卡”按钮及本次额度说明；提交后防止重复点击。
6. 最近找卡入口，按账号隔离，支持删除记录。

不要求先选择完整组合、艺人、专辑和来源。用户只有模糊记忆，也应能开始。

### 4.3 结果页：小卡为主，对话为辅

示意结构：

```text
＜ 描述找卡                          找卡记录

你的描述：黑发、白衣服、蓝色背景，比耶
[艺人：未限定] [蓝色背景 ×] [白色衣服 ×]
[只看已拥有：关]                     编辑条件

已找到一批可能相关的小卡
优先匹配：背景、服装；动作尚不确定

┌─────────────┐  ┌─────────────┐
│   小卡图    │  │   小卡图    │
│   艺人名称  │  │   艺人名称  │
│   来源/版本 │  │   来源/版本 │
│   匹配线索  │  │   匹配线索  │
└─────────────┘  └─────────────┘

可选追问：记得是自拍还是舞台造型吗？
[自拍] [舞台造型] [不确定]

[ 再补充一点描述……                 ] [更新结果]
```

结果列表使用双列小卡网格，卡面尽量完整展示。首屏优先加载少量候选，更多结果分页；没有必要先给一大段解释再展示图片。

顶部保留原描述及当前条件；底部固定“补充描述”输入区域。键盘关闭后仍能看见候选。完整对话历史放在“本次描述记录”中按需展开，避免挤压看图空间。

### 4.4 结果卡显示什么

| 信息 / 操作 | 规则 |
| --- | --- |
| 小卡图片 | 来自真实图鉴，不用生成图代替 |
| 艺人、组合、来源与版本 | 读取正式图鉴字段；缺失就不编造 |
| 匹配线索 | 如“蓝色背景、白色服装”；不确定部分单独说明 |
| 已拥有 / 心愿单 | 复用本人现有关系，只作标识，不自动改变 |
| 点卡面 | 打开现有小卡详情 |
| “就是这张” | 确认搜索命中，进入或定位图鉴详情；不等于“我有这张” |
| “不是这张” | 从当前会话中降低或排除该候选，可撤销，不修改图鉴资料 |

默认不显示“正确率 98%”等未经校准的数字。对相近卡面、不同来源或同套版本，可并列展示并说明差异仍需确认。

结果列表不放自动播放视频；原卡的动态生成操作在详情中承接，保持找卡时的图片比较效率。

## 5. 功能 2：条件、追问与异常交互

### 5.1 条件如何变化

| 用户操作 | 系统行为 |
| --- | --- |
| 首次输入“白衣服、蓝背景” | 解析视觉条件并召回候选 |
| 补充“是某艺人” | 加入艺人范围，保留已有服装与背景条件 |
| 改口“不是白色，是黑色衣服” | 替换服装条件，不能同时要求白衣和黑衣 |
| 表示“可能是蓝背景” | 作为偏好排序，不强制排除其他颜色 |
| 明确“不戴帽子” | 记录否定条件；未确认图片特征不装作已满足 |
| 删除一个条件 | 标记待更新；点击“更新结果”后重新检索，避免每次操作立即消耗 |
| 修改组合 / 艺人范围 | 清楚展示新的范围；保留兼容描述，冲突条件提示用户调整 |
| 重新开始 | 清空当前条件和候选，开启新会话，提交前说明额度 |

“已确认条件”和“模型推测”需要视觉区分；模型猜测的艺人不能自动成为硬筛选。若用户输入一个无法唯一对应的艺名，先让用户确认候选身份。

### 5.2 追问规则

- 有结果时先展示结果，追问是可选辅助。
- 一次只问一个有区分价值的问题，例如服装、手势或自拍 / 舞台场景。
- 每个追问都有“不确定 / 跳过”；用户不回答也可以继续看结果。
- 追问选项来自当前候选或已验证的图鉴字段，不猜测未提供的发行事实。
- 已回答的信息不要重复问。若条件互相矛盾，先指出冲突再更新。
- 用户可查看本次描述记录并回到上一轮结果；历史结果再次展示前仍校验卡片可见性。

### 5.3 找不到时怎么办

| 状态 | 页面呈现与下一步 |
| --- | --- |
| 候选较弱 | 展示“相近结果”，说明哪些条件未确认，提供补充描述 |
| 没有候选 | “暂未在图鉴中找到符合描述的小卡”，可移除条件或重新描述 |
| 用户手中有图片 | “试试 AI 扫描”；只有扫描后的缺卡场景才进入既有缺卡反馈 |
| 查询服务失败 | 保留描述和旧结果，显示本轮未更新；允许重试，不伪装成无结果 |
| 查询超时 | 继续查询原请求状态或重试同一请求，不重复扣次 |
| 额度不足 | 保留输入与会话，可使用普通搜索；说明获取额度方式 |
| 卡片被下架 | 不再出现在新结果；旧页面打开时显示不可用并允许返回 |

用户反馈“这张的来源错了”时，进入原卡的数据纠错流程；“这不是我要找的”只作为搜索质量反馈，两者不能混在一个审核队列中。

### 5.4 页面状态保留

从结果进入小卡详情、查看公开动态、发起生成后返回，保留当前描述、条件、结果顺序、已排除候选和滚动位置。搜索结束不自动添加到已拥有、心愿单或卡册。

快速连续提交时，以最新请求版本为准；迟到的上一轮响应不能覆盖新结果。用户回到历史轮次是明确操作，不等同于旧响应自动回写。

## 6. 功能 3：动态作品的定位与状态

### 6.1 与“已拥有”同级展示，但保留独立关系

推荐命名：

- 导航 Tab：**动态卡**。
- 列表页标题：**我的动态卡**。
- 创建按钮：**生成动态**。
- 小卡详情入口：**让小卡动起来**。
- 原卡关联入口：**我的动态作品（N）**。
- 导出按钮：**保存视频 / 保存 Live Photo**，按当前能力分别展示。

原卡上的“有动态”不是用户手动开关，而是从可用成品计算的提示：

- 对本人显示“我的动态作品 N”，仅计本人未删除且可查看成品。
- 若以后展示平台公开动态，另用“公开动态 N”，只计审核通过且可访问的内容。
- 不对其他用户显示“某人还有 3 个私有作品”等信息。
- 排队、失败、审核处理中的未交付结果不计为成功作品。

### 6.2 建议的数据与操作关系

| 事件 | 已拥有 / 心愿单 | 动态作品 | 原卡 |
| --- | --- | --- | --- |
| 生成成功 | 不变 | 新增一件，默认私有 | 不变 |
| 用户主动再生成 | 不变 | 新任务、新作品，旧作品保留 | 不变 |
| 系统重试同一任务 | 不变 | 最终最多交付一件，不多扣次数 | 不变 |
| 删除动态作品 | 不变 | 从库和播放队列移除 | 不变 |
| 取消已拥有 | 只改变拥有关系 | 保留，只有“仅已拥有”筛选结果会变化 | 不变 |
| 公开作品 | 不变 | 审核通过后可被他人查看 | 原图鉴图片不变 |

计数区分“作品件数”和“来源卡数”，例如“12 件动态作品 · 来自 8 张小卡”。同一卡的多个效果不自动覆盖，也不被误算成新增图鉴卡。

### 6.3 首期生成范围

建议首期只从已有图鉴小卡选择输入，支持“我的已拥有”和“全部可生成小卡”两种选卡范围，暂不开放任意相册照片上传。

每张输入需通过：图鉴和图片可访问、图片质量可用、允许 AI 衍生处理、所选模型可接收、用户额度足够。不可生成的卡保留普通查看与收藏功能，不要求用户先点“我有这张”来解除限制。

## 7. 功能 3：从选卡到成品的页面流程

### 7.1 入口与选卡

| 起点 | 行为 |
| --- | --- |
| 原小卡详情 | 自动选中当前卡，直接进入效果页 |
| 收藏 → 已拥有 | 单卡菜单增加“生成动态”；首期不做批量生成 |
| 收藏 → 动态卡 → 生成动态 | 打开选卡器，优先展示已拥有，可切换全部符合条件的小卡 |
| 找卡结果 | 经原卡详情确认后发起生成，避免误选候选直接消费额度 |

选卡器支持搜索和组合 / 艺人筛选，显示“可生成 / 暂不可生成”及简短原因。没有已拥有小卡时提供全图鉴入口，不出现死路。

### 7.2 效果选择与确认页

展示原卡完整图、可用效果示例、输出规格、扣次说明和生成按钮。

首期提供少量验证过的轻动态模板，例如微风、背景轻动或轻微表情变化；具体可用项由实际模型对艺人图的测试决定。示例视频应标“效果示例”，不能保证本卡完全复现。

建议默认无声、单镜头、保留原卡构图；目标成品约 3 秒。实际调用的时长、分辨率和后处理由后台按模型能力确定，提交前明确交付规格。

首期不开放任意自由视频提示词，减少用户理解成本和不稳定效果；后续若支持，可先做“补充描述”并继续约束动作幅度。

确认区建议文案：

```text
生成 1 件动态作品
效果：轻动态
成品：App 内播放 + 视频保存 + 1 张 Live Photo
当前设备：已通过 Live Photo 保存适配
消耗：1 次动态生成
作品默认仅自己可见
[生成动态]
```

以上示例是本稿建议的已适配 iOS 档位，包含 1 张 Live Photo，有效封装属于任务成功条件。未适配设备采用明确的视频档位；不能展示示例中的 Live Photo 承诺，也不能用“已生成 Live Photo”宣传视频。输出档位在任务创建时固定，不能生成后再更改承诺。

### 7.3 等待与任务恢复

创建后显示任务页，可返回继续使用 App。动态库顶部提示“有 1 个作品生成中”，点击进入生成记录。

用户状态：排队中 → 生成中 → 处理中 → 已完成；异常进入失败 / 取消 / 状态待确认。处理中可能包含检查、转码和封装，供应商成功不等于全部完成。

不显示未经估算的精确进度百分比。完成后发送结果通知，点击直接打开对应作品。再次打开 App 仍能恢复原任务；关闭页面不取消模型执行。

### 7.4 成品确认页

自动播放或按用户播放偏好展示结果，同时提供：

- 查看原卡：打开原始卡面或原图鉴详情。
- 保存视频 / 保存 Live Photo：只展示当前支持的格式。
- 分享 / 公开：进入明确的权限与发布流程。
- 再生成：保留当前作品，重新确认效果和额度。
- 删除：移除本作品，不删除原卡。
- 效果有问题：提交质量反馈，说明失真、动作异常、文字变形等。

有效交付后用户单纯“不喜欢”不自动触发无限免费重做；技术失败或明显不符合交付标准的结果按明确规则补偿。

列表数量跟随当前筛选展示，顶部可以另标全部作品数。暂不可播放的作品显示原因与可用操作，不计入连续播放队列。

## 9. 功能 3：上下滑全屏播放

### 9.1 借鉴短视频播放交互，首期限定播放范围

支持上下滑，一屏一件作品，当前作品按设置循环播放。列表来自用户明确进入的集合：

| 进入来源 | 播放队列 | 播完后 |
| --- | --- | --- |
| 我的动态卡 | 当前筛选和排序下的可播放作品 | 显示“已看完”，返回图库或重新播放 |
| 本人某张原卡的作品列表 | 该来源卡的本人作品 | 不自动切到其他艺人或公共推荐 |
| 他人公开主页 | 该主页当前可访问的公开作品 | 到底结束，不混入其私有作品 |
| 单件分享链接 | 该单件作品 | 可主动进入作者公开主页，不自动追加推荐 |
| 后续动态合集 | 合集内按指定顺序的可访问作品 | 按合集结束 |

首期上下滑播放器不等于抖音式推荐社区。不新增推荐算法、热门榜、评论、直播或陌生人私信。

### 9.2 页面布局

```text
＜ 我的动态卡 · 当前筛选                      ⋯
                      3 / 12

             原比例动态小卡
          完整保留卡边与重要文字
             画面居中播放

                                      [原卡]
                                      [保存]
                                      [分享]

艺人名称 · 来源/版本
效果名称 · AI 生成动态

```

短卡面不强行裁成 9:16。剩余区域可使用纯色或原图模糊背景适配屏幕；这是显示适配，不属于本期排除的 AI 素材生成。

### 9.3 手势与操作

| 操作 | 行为 |
| --- | --- |
| 上 / 下滑 | 切换队列中的下一件 / 上一件，保留队列顺序 |
| 单击画面 | 播放 / 暂停，并提供可见的播放控件 |
| 长按画面 | 暂停并查看清晰静态帧，松开恢复原状态 |
| 返回 | 回到原图库及滚动位置 |
| 查看原卡 | 打开原图鉴详情；返回恢复本作品和播放位置 |
| 保存 | 展开当前可用导出格式，不重新生成 |
| 分享 | 按本人 / 访客权限显示对应入口 |
| 更多 | 本人可删除、管理公开状态、反馈效果；访客可举报 |

首期不把双击做成“加入心愿单”或“已拥有”，避免播放习惯导致实体卡关系被误改。暂不做动态作品点赞和收藏，后续若增加，应建立独立关系。

### 9.4 播放性能与可访问性

- 同时只播放当前作品；离开页面、进入后台或被其他媒体打断时暂停。
- 默认无声。关闭自动播放或开启减少动态效果时，显示封面，用户点按播放；不能必须依赖手势才能操作。
- Wi-Fi 下可有限预取下一件；移动网络默认先加载封面和当前视频，不预下载整库。
- 加载失败保留封面，支持重试或跳过；不自动重跑 AI。
- 用户正在播放时不因新作品到达而打乱当前顺序；刷新列表后更新。
- 公开作品被撤回、删除或限制时，拒绝不再具备权限的后续请求，并从访客 / 公开播放队列移除；转为私有后，本人在自己的库中仍可播放允许查看的成品。不能仅靠 App 隐藏入口。
- 依赖浏览签名链接和合理缓存控制，撤回后无法追回用户已经下载或录制的副本，界面不承诺这种能力。

## 10. 是否增加“动态相册”或合集

建议分成三层理解：

| 形式 | 解决的问题 | 本期建议 |
| --- | --- | --- |
| 相册式网格图库 | 看全量成品、筛选、查找与管理 | 做，作为默认管理页 |
| 动态合集 | 将若干动态作品整理成“某艺人合集 / 回归纪念”等 | 下一阶段，可在需求确认后增加 |
| 现有 BOOK / CARDS 放入动态作品 | 编辑、翻页或卡片舞台中播放视频 | 单列后续需求，不能仅靠视频链接接入 |

若增加合集，建议采用轻量规则：

1. 合集保存名称、封面、作品引用和排序，不复制视频。
2. 同一作品可加入多个合集；删除合集不删除作品。
3. 点击合集可看网格，也可按合集顺序连续播放。
4. 合集不产生第三种卡册作品类型，不提供 BOOK / CARDS 模式转换。
5. 公开合集只能展示其中已公开且可访问的作品；加入合集不自动公开私有作品。
6. 合集计数、封面和播放队列均按访问者权限计算，不能通过封面泄漏私有内容。

这样先验证用户是否真的需要“整理动态”，再决定是否投入复杂翻页相册、动态排版和导出渲染。

## 11. 个人主页、公开与分享

### 11.1 默认私有，公开需明确操作

本人主页展示自己可查看的所有动态成品及状态；访客只看审核通过的公开作品。生成记录、输入材料、失败原因和额度信息只对本人及有权限的后台开放。

“生成完成”“内容检查通过”“公开审核通过”是不同状态。通过生成检查不自动发布；公开被拒也不自动删除本来允许私有保存的作品。若属于不允许保留的内容，单独限制并说明。

### 11.2 本期分享方案

| 操作 | 规则 |
| --- | --- |
| 本人保存到系统相册 | 私有成品也可在满足输出权限时保存 |
| 本人分享文件 | 用户主动导出后调起系统分享；不会自动公开整份作品库 |
| 分享平台链接 | 作品需公开且审核通过；私有作品提示先申请公开 |
| 主页公开展示 | 审核通过后出现在“动态卡”Tab |
| 转为私有 | 平台公开入口失效，个人库保留 |
| 访客保存 / 再生成 | 首期不默认开放保存作者文件；可查看原卡，再按自身权限生成新作品 |
| 举报 | 对公开作品提供举报入口，关联动态作品 ID，不当作图鉴字段纠错 |

作者头像 / 昵称可链接主页；作品展示 AI 生成说明和原卡入口。公开作品的创作者归属与图鉴原图贡献者分别记录，生成者不能因此成为原图鉴卡的贡献者。

若以后允许“收藏别人的动态卡”，应新建动态收藏关系，不加入原卡心愿单或已拥有，也不计为自己的创作。作者撤回后，收藏引用显示不可用。

## 12. 功能 2 的服务与后台

### 12.1 查询流程

描述 + 会话上下文 → 解析明确条件与模糊偏好 → 正式字段过滤 + 视觉描述 / 图文向量召回 → 候选排序 → 校验 Card ID、当前图片与发布状态 → 返回卡片、匹配线索和一个可选追问。

原有扫描图像特征索引继续独立使用。文字找卡需要新增语义索引，允许先以视觉描述配合字段检索起步，再加入图文向量。

机器生成的服装、背景、动作标签只作为搜索辅助，不能自动覆盖官方图鉴身份、来源或年份。模型解释不能越过真实数据库结果另造卡片。

### 12.2 后台功能

| 后台页面 | 内容与操作 |
| --- | --- |
| 描述找卡配置 | 功能开关、可用范围、模型、最多轮次、输入长度、候选数和预算 |
| 搜索索引 | 已建 / 待建 / 失败 / 失效，图片与模型版本、增量更新、重建 |
| 搜索质量 | 匿名化或受权限保护的样本、无结果、用户确认命中、排除候选、纠错线索 |
| 搜索词与别名 | 经审核维护艺人 / 组合别名，用户私有备注不得写入全局别名 |
| 评测集 | 同人近似卡、姿势、服装、否定、口误修正、多语别名和不存在的卡 |

换图和发布状态变化触发更新；下架立即影响返回结果，不等待整个索引重建。切换向量模型需重建匹配版本，不能混用不同空间的向量。

后台通过搜索失败样本改善检索，不把“用户说不是这张”自动变成图鉴改图或删除操作。

## 13. 功能 3 的服务与后台

### 13.1 统一 AI 接入，但业务流程分别处理

本期统一服务只接入：找卡理解 / 检索相关模型、图生视频与后处理。图片素材生成配置不纳入本期。

App → Fan OS 场景 API → 权限与额度校验 → 搜索处理或异步视频任务 → 业务结果。

共用模型接入、密钥、预算、任务追踪和成本报表；找卡短请求与视频重任务分别限制并发。长期生成不能持续锁住数据库用户记录。

### 13.2 动态生成任务

| 阶段 | 服务端工作 | 用户看到什么 |
| --- | --- | --- |
| 资格检查 | 核对源卡、图片版本、处理条件、效果、设备交付档位 | 不可用原因，尚不正式扣次 |
| 预占与排队 | 固定配置版本、预占额度、创建幂等任务 | 排队中 |
| 生成 | 提交供应商任务并保存任务 ID，查询或验证回调 | 生成中 |
| 后处理 | 转存、检查、裁切、静音、封面、转码；按承诺封装 | 处理中 |
| 交付 | 文件完整且满足约定规格，创建唯一动态作品并结算 | 已完成 |
| 公开 | 用户另行申请，审核当前作品版本 | 待审核 / 已公开 / 未通过 |

同一任务的多次供应商尝试分别记成本，但最终最多创建一个可交付作品。同一原卡主动再生成是新任务。

### 13.3 后台分为业务页与公共配置

| 模块 | 关键字段 / 操作 |
| --- | --- |
| AI 服务管理 | 供应商、模型与接口版本、地域、密钥引用、预算、并发、熔断 |
| 动态效果管理 | 效果名称、示例、输入条件、动作模板、成品规格、是否支持 Live Photo、版本 |
| 可生成卡范围 | 原卡、图片版本、是否允许 AI 衍生处理及依据、限制原因 |
| 生成任务 | 用户、原卡、效果、承诺档位、上游任务、状态、耗时、实际费用、退次记录 |
| 动态作品 | 作者、原卡、成品文件、公开范围、内容状态、封面、创建时间 |
| 公开审核 | 播放成品、查看原卡、审核说明、通过 / 拒绝、下架与举报处理 |
| 成本与质量 | 可交付率、失真反馈、平均有效成本、封装成功率、重复失败等 |

资料纠错、小卡缺失收录、动态作品审核分别处理；可以关联原卡，但不能共用一套“已收录”结果冒充生成成功。

### 13.4 原卡变化的影响

- 新任务始终使用当前允许处理的图片版本；旧作品保留实际输入版本和来源快照。
- 原卡名称或来源修正时，入口读当前图鉴资料，生成历史仍保留当时输入记录。
- 原图更换不会自动重生成或悄悄改动用户旧作品。
- 原卡普通下架时停止新生成，原卡链接按权限隐藏；既有衍生作品是否可保留按下架原因和独立使用依据判定。
- 若下架涉及图像授权撤回或生成内容本身不可展示，需要限制对应衍生作品、公开链接和后续导出，后台应能按来源追溯影响范围。

## 14. Live Photo、失败处理与权益

### 14.1 三种交付能力分别展示

| 能力 | 一期要求 |
| --- | --- |
| App 内播放 | 核心能力；封面 + 视频、可恢复任务及播放状态 |
| 视频保存 | 在支持的设备完成文件保存及权限适配 |
| iOS Live Photo 保存 | 推荐作为已适配 iOS 档位的完整交付要求；独立封装和真机验收后开放，失败不能假称已生成 |
| Android 系统动态照片 | 按验证通过的设备能力开放；否则只承诺 App 播放及视频保存 |

Apple 文档要求 Live Photo 资源及元数据能够有效配对；加载接口不等于将任意 MP4 和图片自动合成为实况照片。[Apple PHLivePhoto 文档](https://developer.apple.com/documentation/photos/phlivephoto/request%28withresourcefileurls%3Aplaceholderimage%3Atargetsize%3Acontentmode%3Aresulthandler%3A%29?language=objc)

真人艺人图片的适用条件也需对具体模型验证；供应商的图生视频能力不代表所有真人参考图均可直接输入。[火山视频生成说明](https://docs.volcengine.com/docs/ark/video-generation-tutorial?lang=zh)

### 14.2 找卡额度：建议按一次找卡会话，而不是每句话购买

为保持连续追问体验，本版建议：**1 次找卡额度含最多 5 轮有效 AI 分析**，作为可调整默认值；后台仍逐轮记录费用。

- 开始时预占 1 次；第一轮成功返回有效响应后确认扣减，正常无结果也属于完成一次分析。
- 追加描述或修改语义条件后，用户点击更新才执行；界面显示本会话剩余轮数。
- 仅使用已有结构化字段过滤、分页和打开详情不消耗 AI 轮次；如需要重新理解或语义排序，则计一轮并在操作前提示。
- 系统失败的轮次不消耗轮数；同一请求重试不重复计量。首次分析失败且终止时退回会话预占。
- 后续某轮失败不退还此前已有效使用的整场会话，但该失败轮可重试。
- 用满轮数后仍可浏览既有结果；继续 AI 分析需明确开始新会话并告知消耗。
- 建议会话有效期 24 小时；到期可回看历史，但继续分析开启新会话。具体免费次数和会员额度另定。
- 会话最大轮数、输入长度、模型调用次数和预算都在服务端限制，不能只依赖 App。

与上一版逐次分析的讨论相比，这一口径更适合自然追问；会员主 PRD 后续需同步采用同一计量单位。

### 14.3 动态生成与导出扣次

1. 创建任务预占，满足已确认交付档位后扣减；系统失败释放，实际供应商成本另记。
2. 排队中取消可退回；运行中能否取消取决于上游，不能把退出页面当作取消。“请求取消”不等于“已取消”：上游确认前显示取消处理中并继续核对，不立即退次；若不支持取消，说明任务仍继续并按约定交付。最终确认取消后释放预占，迟到成功不再重复发作品或扣次，可能产生的上游费用照实记录。
3. 承诺包含 Live Photo 的任务，封装失败先只重试后处理；最终无法交付时退回，不强行用视频替代完成。
4. 原本承诺 App 播放与视频的任务，交付后可结算；后续可选格式导出失败不重新调用模型、不重复扣生成次数。
5. 系统相册权限不足时保留成品，允许再次保存；成功保存、重复下载和查看不扣生成次数。
6. 上游状态未知先查原任务，避免超时后自动并发创建多笔付费调用。
7. 重复回调、迟到结果、补偿与退款通过唯一任务和账本核对，不多发作品或重复扣次。
8. 会员到期保留已生成作品；新生成按当前额度控制，技术和内容限制仍然生效。

本稿不确定新的售价。成本统计按“每次完整找卡会话”和“每件有效动态作品”，包含全部模型轮次、失败尝试、后处理和流量。基础云 ¥2,000/月不能直接视为覆盖所有新增视频调用。

## 15. 数据与权限要点

| 数据对象 | 必需内容 |
| --- | --- |
| 搜索会话 | 用户、原描述、当前条件、范围、轮次、候选版本、排除列表、命中反馈、额度关联 |
| 搜索轮次 | 输入、已确认 / 模糊条件、查询版本、实际模型调用、返回 Card ID、成本 |
| 动态任务 | 用户、源 Card ID、图片版本、效果版本、承诺档位、上游尝试、状态与扣次 |
| 动态作品 | 独立 ID、作者、源卡、封面、视频、可用导出资源、技术可用状态、创建时间 |
| 公开申请 | 作品版本、期望可见范围、审核状态、审核记录、发布时间 |
| 关系 | 已拥有 / 心愿保持原表；动态归属、后续合集及动态收藏独立维护 |

关键规则：

- 每次读取作品、播放文件或导出都校验权限；知道作品 ID 不等于可以访问私有视频。
- 原卡数据、作品作者和生成来源不能由客户端任意改写。
- 公共主页及播放队列只返回可访问成品，不暴露私人任务与文件地址。
- 发布审核针对确定作品版本，不能审核 A 文件后客户端替换成 B。用户在待审期间撤回、转为私有或删除时，该公开申请失效；迟到的审核通过不能重新公开，生效前同时检查作品版本、当前状态和仍有效的发布申请。
- 作品转私有 / 删除后，平台分享和主页相应变化；后台留存必要任务、费用及审核追溯。
- 搜索模型只负责理解与排序，不可自行执行收藏、拥有、生成、扣费或公开操作。
