# 九张卡册照片分割修复

2026-10-11，用户提供的卡册照片已从整页一个对象改为 **9 张独立裁剪、9 个独立识别对象**。每张卡继续单独匹配图鉴与等待确认；裁剪成功不等于图鉴匹配成功。本次不改变 API 数据结构，也不改 App 的上传、收藏或确认逻辑。

## 原因与修复

原图为 1080×1487，主卡册页包含 3×3 完整小卡，上方及左侧有不完整的邻页卡。旧检测的 Canny 闭合操作把透明卡套缝线、反光和卡内纹理连接起来，得到接近整张照片的大外框，未提取九个卡面。App 只是完整展示服务端返回的一个对象，没有截断或合并多卡结果。

新增透明卡套辅助检测，按方向长边、矩形尺寸、行列一致性提取卡面。只接受具备边界与内部纹理证据的区域，少量断开的边线会在局部范围内校正；没有固定九张，也没有把整张照片机械等分。空袋和画面边缘不完整的卡不会仅因位置像网格就强行补齐。

普通单卡、散放卡、透视卡的原有轮廓检测仍保留。所有区域各有独立裁剪图片、Detected Card ID、候选、状态及用户确认，不会自动增加 Owned。

## 原图验证

使用真实开发库的只读 SQLite 备份运行完整识别服务，照片和扫描写入隔离目录，没有修改原扫描历史或收藏。修复前结果为 1；修复后检测数、服务结果数、独立 ID 数均为 9，并已检查九张裁剪图。

- 检测报告：`output/scan-nine-qa/final/regions-im05o71v/report.json`
- 九张裁剪预览：`output/scan-nine-qa/final/regions-im05o71v/card-crops.jpg`
- 框线预览：`output/scan-nine-qa/final/regions-im05o71v/detected-regions.jpg`
- 单卡裁剪：同目录 `crop-01.jpg` 至 `crop-09.jpg`

验证时有效官方图鉴索引为 1 张，本照片九张没有对应命中，结果仍分别为“未识别”。**这是图鉴参考不足，不再是整页未拆分**。需要在后台上传对应官方卡面并建索引后，才能验证具体卡版匹配；没有补造候选或相似度。

## 回归范围

新增中性合成卡册测试，包含低对比灰底、圆角、透明缝线、反光和邻页截断卡：3×3 为 9 张，2×3 为 6 张，中间空格为 8 张，轻微倾斜保持实际数量。API 测试覆盖九个独立裁剪、八张有图鉴参考加一张未知、批量确认其余八张及历史独立状态。Flutter 测试覆盖九对象完整解析、九张裁剪展示、单张选择／取消互不影响，以及同版重复实物按独立 ID 提交。

本次全量后端 **152 项 pytest 通过**，Flutter **62 项测试通过**（两个需主动开启的 API 契约测试在普通运行中跳过）。Dart 静态检查通过；本次检测代码、测试与验证脚本的 Ruff 检查通过。其他正在更新的后台文件有 7 个行长检查提示，未改动这些无关文件，也未宣称全仓 Ruff 通过。

原图缩放及轻微倾斜已检查；严重旋转、强透视、遮挡或缺乏边界的照片仍可能漏检，退回原检测路径，不保证所有卡册都能准确计数。这是局部几何改进，不是已验证的生产级目标检测模型。窗格、照片墙等也可能呈矩形网格，因此保留官方匹配及用户确认，不将几何检测结果直接入库。

## 使用方式

后端修复生效后，现有 iOS App 重新从相册上传同一原照片即可。旧扫描记录保存的是当时的一个结果，不会自动重算；需重新扫描，不是刷新旧结果页。无需 iOS 重打包、数据库迁移或重置数据。

复跑原图隔离验证：

```bash
cd apps/api
.venv/bin/python scripts/verify_scan_regions.py \
  --image data/uploads/scans/current-user/882d7168b909400e9133a361bec1545c.jpg \
  --source-db data/fan_os.db \
  --output ../../output/scan-nine-qa/recheck \
  --expected-count 9
```

该脚本以只读连接备份源数据库，只在新的验证目录存储扫描和裁剪。

主要代码为 `app/integrations/card_matcher/sleeve_detector.py` 与 `adapter.py`；回归为 `tests/test_scan_sleeve_detection.py`、Flutter `test/scan_session_test.dart`。
